# output3 缓存与帧率现场排查

日期：2026-10-29。车机实际安装output3，PID6497，APK SHA `579be0293691825d7d4e8d667b7da46fed5778265c3d6230394f984b1990ab2d`。用户认为画面不连续可能来自缓冲积压；本轮只读检查，未调整缓冲、帧率或系统配置。

## 缓冲容量与测量边界

| 环节 | 当前实现/现场值 | 能说明什么 |
| --- | --- | --- |
| USB NCM读取块 | 32 KiB | 单次读取工作缓冲，不是32 KiB视频预缓冲 |
| NCM网络帧队列 | 上限256个以太网帧或1 MiB | 网络包而非256张画面；recv先消费已有包，不等待填满；未测出实时占用 |
| 视频TCP socket | 请求524288 bytes；ServerSocket与accepted socket回读均262142 bytes | 约256 KiB的SO_RCVBUF核算值，不是已缓存的视频字节数，也不是等到填满才读取 |
| 系统rmem_max | 131071 bytes，rmem_default=110592 | 与SO_RCVBUF约双倍回读吻合；内核记账规则见官方手册，不能直接当TCP有效载荷容量 |
| 接收与解密间独立队列 | B未启用C的10消息/4 MiB队列 | B在接收线程读取完整消息、解密后同步送给媒体sink |
| 解码前应用队列 | 上限60帧或8 MiB，帧龄检查250 ms | 上限不是实际占用；本轮没有实时队列条数/字节数日志，不能说已经堆满60帧 |
| 硬件解码内部 | 未取得内部队列容量与占用 | CODEC_AGE为应用输入至输出取出耗时，不能换算成内部缓存大小 |
| 已解码输出选择 | 每批零超时读取，最多8输出，保留最新候选显示 | 8不是等待凑满的缓冲目标；旧画面会被归还并计为superseded |

TCP读回证据：08:21:31.020 `requested=524288 actual=262142`，08:21:31.050 `receiveBytes=262142`。视频流type110，端口35378（0x8A32），进程UID10062。现场 `/proc/net/tcp6` 对该连接60次采样（约100ms间隔），59次rx_queue=0，一次702 bytes，未观察到持续TCP接收堆积；采样不能排除间隙中的瞬时突发或手机侧/USB层积压。

资料：[Linux SO_RCVBUF语义](https://man7.org/linux/man-pages/man7/socket.7.html)、[内核TCP队列字段](https://docs.kernel.org/networking/proc_net_tcp.html)。

应用队列已有真实延迟：08:24:06平均57.676ms、最大289.814ms并触发恢复。08:24:11平均9.778ms、最大137.383ms；同窗从媒体sink接收至Surface提交平均83.204ms、最大241.021ms，提交间隔平均32.929ms、最大201.776ms。08:24:16平均队列59.780ms、最大221.667ms，提交平均130.438ms、最大286.717ms。B的 `RECEIVE_TO_SUBMIT` 起点在解密后媒体sink，**不包含USB传输、TCP读取及解密之前的延迟**。

本次08:23:26之后记录3次250ms积压恢复、已有IDR追帧命中0。统计证明应用队列积压和输出节奏不均存在，不能证明“TCP缓存太大”或所有断续只由这一层造成。接收本身也未稳定60fps，输出合并与恢复进一步减少提交帧数；最初缺帧来自手机发送、USB/TUN调度、接收处理还是系统争用，仍需区分。
