# ADR-0007：H53 重启后的 DiPlay VPN 授权恢复

状态：Proposed（实现已随历史候选装车，但VPN重启授权问题尚未解决；不等同于仅本地候选或已实车验收）

日期：2026-10-30

作者：Codex

最后修改：2026-11-03

## 上下文

2026-11-03状态核对：USB带线启动的一次恢复成功不证明VPN授权已恢复。后续已装及未装候选均保留此实现，但VPN问题仍列未解决，见[当前状态](../GEELY-8600-STATUS.md)。以下设计及最初测试边界保留原意。

H53 `06.03.08600.H53.00060` 的 Vpn 将当前授权包存在系统内存，构造时初始化 `[Legacy VPN]`，不跨系统重启保存。DiPlay 现有 prepare 检查正确，但用户每天开机需再次确认。目标是在已确认信任后减少重复操作，用户授权先本地开发、验证、打包，装车另行验收。

## 决策

仅 geelyUsb、固定包 `com.shihab.diplay.repair1.geely8600`、API18/C3ALFUS/精确 H53 display、manifest 明确 opt-in 生效。`GeelyVpnConsentRecovery` 在系统 prepare 确认已授权后记录内核 boot_id；拒绝时清除。仅新 boot、已有信任且本 boot 未尝试时允许一次恢复。

复用现有 `GeelyUsbOemBridge` 固定命令启动 DEX035/API18 单次 `GeelyVpnConsentHelper`，不添加任意命令/包名/UID 参数。助手校验固定私有租约、nonce、当前 boot、4秒 elapsedRealtime 截止时间及平台，以固件已有 Process.setGid/setUid 降至1000。查询并拒绝现有 legacy runner；系统 prepare 用 `[Legacy VPN]` 到固定包的 owner 比较更新，随后查询复核。应用最终仍依据 VpnService.prepare 判断是否需要系统授权。

恢复在后台执行，调用方最多等待5秒，助手 watchdog6秒，未退出的 OEM Binder 保持单飞，租约在结束/Activity销毁时截断并删除。普通变体与其他车型保持原授权流程。不改固件、不改系统文件、不为权限失败安装root，不更改媒体实现。

## 后果

正面：首次系统确认保留，同 boot 内撤销不会自动重新授权；系统授权与本地信任职责明确；其他应用 VPN owner 受系统原子比较保护；现有内建 VPN runner 被保守拒绝。

负面与准确边界：

- 原厂 `getLegacyVpnInfo` 与 `prepareVpn` 是两个 Binder 调用，不能原子保护“恰在检查后新启动”的内建 VPN。这一并发边界未被消除；本候选的使用条件是不用系统内建 VPN 与 CarPlay 同时启动。
- 已经发出的 Binder 授权请求不能通过租约或超时撤回；取消只阻止尚未发出的调用。调用结果不明时回读真实系统授权，已经授权就继续，未授权才显示系统确认；不为了制造弹窗而撤销已有授权。
- 对应用未观察到、紧接着又发生重启的外部撤销，历史信任标记不能可靠识别。这不是系统级永久授权或全局撤销审计机制。
- 特权桥和实际固件安全策略仍需实车核验；通用API18模拟器只能验证方法签名、UID切换、Binder及局部租约机制。

## 替代方案

- 只保存应用“已授权”布尔值：不能代替系统内存状态，建立隧道仍失败。
- 自动点击系统信任窗口：依赖界面且不能保留明确首次确认，不采用。
- 改系统 Vpn 持久化、替换 VpnDialogs 或刷固件：扩大系统变更与回滚范围，不采用。
- 直接root调用prepareVpn：固件拒绝root，不成立。
- 改走无 VPN 的用户态网络栈：改变USB媒体传输架构，超出本次范围。

## 撤销条件

原厂桥不可用、系统 UID 调用失败、实车体验退化、需要并发使用系统内建 VPN，或用户要求每次重新确认时，撤销 geelyUsb `GEELY_VPN_RESTORE` opt-in 或同签覆盖原基线包；保留系统正常确认。不卸载、不清数据。若普通系统提示已经拒绝，本地信任自动清除。
