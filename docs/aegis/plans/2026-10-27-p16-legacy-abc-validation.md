## A：P16 网络和调度优化

修改 owner：`shared/src/main/java/com/shilapi/xcertplay/airplay/AirPlaySession.kt`、`ScreenStream.kt`，及 `media/AndroidMediaSink.kt` 的视频工作线程入口。统计复用 `StreamReceiveStats.kt`、`VideoStats.kt` 和既有诊断输出。

实施顺序：

1. 触控 event socket 在交给工作线程前设置 `TCP_NODELAY`，保留加密、写锁、关闭和重连顺序。
2. 视频 ServerSocket 在 bind 前申请 512 KiB 接收缓冲，accept 后回读实际值；不改系统 sysctl，不提高既有队列/帧龄限制。视频端 `TCP_NODELAY` 只影响本端发送，不宣称它控制 iPhone 发视频。
3. 调度策略仅针对匹配平台的视频接收和解码工作线程，由线程自身设置 nice=-8，失败保留原行为。提供会话开始前可确定的诊断开关，先关闭再开启作轮内对照；不把音频、USB、UI 全部提高优先级。

离线验证：本地 socket 选项、重连与设置失败回归；相关事件加密和视频接收测试；API 18 兼容检查。共享线程行为由独立审查覆盖。

现场验证：先以调度关闭状态测试网络改动，再打开调度重复同场景。记录实际缓冲及线程优先级，不以“设置成功”当性能收益。重点观察滑动响应、接收间隔、音频缺口及 CPU 竞争。

通过条件：连接不回归，画面/触控至少有可重复改善且音乐不变差。调度开启导致声音恶化时，保留关闭状态；整轮没有明确收益则记录“无明确收益”，不强行纳入下一包。

## B：Legacy 原生媒体解密

修改 owner：`airplay/AirPlayCrypto.kt`、`ScreenStream.kt` 的 `ScreenCodec.decryptFrame()`、`AudioStream.kt`；新增职责单一的 `airplay/NativeChaCha.kt` 及对应 JNI/C 源文件；沿用本项目 native 构建和测试位置。

调用方边界：当前 `chachaOpen()` 还用于 `ControlCipher`、`IapTunnel`、`PairSetup`、`PairVerify`、`VideoSettingsChannel`。第一版仅让媒体调用进入 native，保留这些控制/配对调用的原路径；实施前全量检查调用方。媒体包装入口仍保证输入密文不被修改、输出和错误语义一致，不能照抄 Legacy 的原地覆盖契约。

实施顺序：

1. 选择性引入经过源码核对的 ChaCha20-Poly1305 C 实现与 JNI；保留来源和许可证，保持 nonce、AAD 和标签校验。
2. 核验现有 NDK 对 API 18 的实际支持、`.so` 动态符号及 ARMv7 ABI。Legacy 的 API 19 构建参数不能原样照搬并声称兼容。
3. 加入 RFC 向量自检、长度/边界/篡改检查、结果与旧实现对照，以及加载失败回退。标签失败必须拒绝帧，不能被当成可忽略的 native 故障后放行。
4. 保留会话级的 native 开/关对照入口和成功/失败/回退累计值；不在同会话随意改变密码状态。对大帧测 JNI 持有数组期间的耗时，不能用 native 名称推定更快。

离线验证：正反向向量、错误 key/nonce/AAD/tag、空/截断/边界帧、输入未修改、多线程调用、加载失败及退回旧实现；密码代码变更必须经新的独立 agent 审查后才进入安装候选。新增 native 技术选型实施时按项目 ADR 约定记录，不能预先写成已验收。

现场验证：首先确认 API 18 加载和自检通过、音视频 native 调用计数增长，再对比纯解密耗时与整体 CPU、GC、音频供给。不能因回退到 Java 后“仍能播放”就认为 B 的性能路径通过。

通过条件：native 路径真实生效，认证失败率不升高，解密耗时有可重复改善且整体音画不退步。若耗时改善但音乐仍卡，只记“解密优化通过、音乐问题未闭环”，不扩大结论。

## C：视频接收解耦和恢复治理

修改 owner：`airplay/ScreenStream.kt`、`media/AndroidMediaSink.kt`、`VideoDecodeQueue.kt`，及现有测试 `VideoDecodeQueueTest.kt`、`StreamReceiveStatsTest.kt`；按现有位置补视频接收生命周期测试。

实施顺序：

1. 接收线程负责读取、校验长度和分配 nonce，独立工作线程顺序解密。配置帧与视频帧必须保持原顺序；关闭和新会话开始后不得交付旧帧。
2. 参考 Legacy 的 10 帧、最多 30 ms 等待机制，但同时限制总字节与帧龄。总字节上限在离线实现时结合内存预算确定并记录，不能把“10 帧”当成低内存保证；原有帧长防护保留。
3. 排队失败/丢帧仍消耗对应接收 nonce，并通知参考链已断，按节流机制请求 IDR。不能任意丢掉参考帧后继续无提示地解码后续 P/B 帧。
4. 将恢复原因明确分类。首选 Legacy 思路：对已正常输出、格式/Surface 未变化的短时积压尝试保留解码器、等待新 IDR；不对所有错误统一软恢复。
5. P16 的 `flush` 保留为同一 C 轮的条件性对照策略：仅前述条件满足且保留实例方式仍有积压问题时试验。两种策略互斥，明确记录当前策略，避免保留→flush→重建循环无界叠加。
6. 首帧前、格式/Surface 变化、非法输入、容量不足或硬件异常继续原重建路径。flush 后丢弃旧 indices，并按 API 18 正确取得 buffers；已送新关键帧仍持续无输出则有界降级重建，本会话禁用失败策略。静态页面没有新输入不判故障。
7. 第一版保留 250 ms 过期阈值，不直接照搬 Legacy 的 800 ms。只有采样证明需要，才另做阈值对照；变顺但触摸明显变慢不算通过。

离线验证：nonce 连续性、队列字节/帧数上限、配置顺序、超时/中断/关闭/重连、参考链恢复、首次输出前不 flush、flush 异常与降级、Surface/格式变化。独立 review 覆盖共享状态、竞态和恢复边界。

现场验证：先验证队列且保留旧恢复，再启用候选软恢复，必要时才试 flush。至少实际覆盖一次积压恢复；自然场景未触发时，可在停车、隔离诊断构建中执行一次有界延迟注入，明确记录并从最终包移除。未触发则标为“恢复路径未覆盖”。

通过条件：队列稳定有界，动态画面无持续增长的延迟，无黑屏/花屏/重建循环；真实恢复后画面回来且音乐不恶化。未收益或退步则返回上一通过版本，C 不因版本更新而自动成为最终版本。

## 明早现场顺序与协作

1. 用户停车，手机解锁，车机连手机热点，启动原 Termius Remote 转发并保持前台。USB 使用之前成功的接口；如有 USB 授权提示由用户允许。
2. 用户在本对话告知“已就绪”。届时按既定渠道重新确认 107 实例、转发、ADB 和车机身份；旧 IP/端口仅作线索。107/Termius 只负责 ADB，CarPlay 音画应继续走 USB NCM。
3. 读取当前安装包和参数；采集 USB2/统一诊断基线。不要直接覆盖旧包后才发现没有对照数据。
4. 顺序安装并核验 A → B → C，各轮先短测连接，再跑相同操作。根据上一轮结果剔除失败策略，必要时回到父版本重复对照。不会要求用户每轮重新授权既定范围的安装和采样，只在需要实际操作时发一个简短提示。
5. 每轮固定五分钟：一分钟缓存音乐+静态页、两分钟列表滑动/页面切换、两分钟地图操作并持续音乐；导航提示可重复时追加同样提示。争议结果复测，不用一次主观感觉定案。
6. 每轮通过前做一次拔插重连；最终候选再做连续十五分钟播放，以及应用离开/返回、Siri/通话中断恢复、车辆正常关机再启动。关车重启条件由用户现场配合，不假定断电等于正常休眠/冷启动。
7. 全部五分钟测试只是初筛；未完成长测、冷启动或恢复路径时保留待验证项。现场时间不足先留下上一通过包，不能为了赶时间把未完成项目标通过。

用户操作手机与 Termius 前台维持可能冲突，操作分段进行。若 ADB 中断，先保存已收到的数据、恢复转发并重新核验会话；不能把远程采样断开直接当作 USB CarPlay 故障。采样命令必须限频，避免大量抓日志/文件传输本身干扰卡顿判断。

当前没有安排定时任务或后台自动执行。实际继续以明早用户就绪消息为触发；此前“暂不采集车机”限制在用户进入现场验证前继续有效。
